# ClickHouse TimeSeries lab — reproducible facts (2026-11-01)

Scope: **moleus/ClickHouse**, branch `lab/timeseries-fastpath-ci`. No upstream writes and no pull requests.

## Pinned code and hypothesis

- Source commit: `52529f0c711566d696917678bf15e7068772fdde` (ClickHouse).
- Experimental patch: `.github/ts-lab-patches/0001-fast-sum-rate-no-duplicate-grid.patch`.
- The existing `dropMetricName()` path removes `__name__` using an extra grouping and per-step duplicate check. For `sum(rate(exact_single_metric_selector[range]))`, that step can be omitted: `sum` removes the labels and the metric name, so any intermediate duplicate detection is not exposed by the final result. Metric-name regexes, explicit `by`/`without`, offsets and other expression shapes use the normal path.
- Code evidence at the pinned commit:
  - `src/Storages/TimeSeries/PrometheusQueryToSQL/dropMetricName.cpp`
  - `src/Storages/TimeSeries/PrometheusQueryToSQL/applyFunctionOverRange.cpp`
  - `src/Storages/TimeSeries/PrometheusQueryToSQL/applyOneArgumentAggregationOperator.cpp`
  - `src/Storages/TimeSeries/PrometheusQueryToSQL/Converter.cpp`.
- The patched code compiled in the local environment using a *syntax-only* Clang check (EXIT 0). This does **not** prove it links or passes runtime tests. The GitHub CI job must do both.
- Five deterministic regression cases are encoded in `.github/ts-lab-scripts/validate_promql.py`. The same tests passed against the unpatched local ClickHouse 26.11.1.974. Patched binary still needs those tests.

## Baseline experiment, before the patch

Hardware: isolated container, 4 vCPU cgroup, 4 GiB memory. Synthetic TimeSeries dataset: ~27.32 million samples, 113,284 time series across six hours; ClickHouse `prometheus.highcard_default`; VictoriaMetrics v1.134.0. Range: 2026-10-30 02:00:00 UTC to 04:00:00 UTC, 60-second step (121 points). Expression `sum(rate(http_requests_by_route_total[5m]))`. `max_threads=2` for ClickHouse.

Five warmed repetitions, alternating request order:

| Path | Wall p50 | Wall range | CPU time p50 | Process peak RSS p50 |
|---|---:|---:|---:|---:|
| VictoriaMetrics MetricsQL `rate` | **284 ms** | 237–304 ms | 0.45 s (vmselect) | 70.54 MiB |
| Unpatched ClickHouse native PromQL | **3,010 ms** | 2,507–3,474 ms | 3.18 s (ClickHouse server) | 990.47 MiB |
| Equivalent manually simplified ClickHouse SQL | **1,969 ms** | 1,741–2,669 ms | 2.11 s (ClickHouse server) | 1,024.72 MiB |

Method: `/mnt/data/build-work/bench_single_node.py --repeats 5`; collected raw output `/mnt/data/tslab-baseline-5x.json`. Peak RSS is absolute resident memory for the observed process, **not** memory allocated by one query. Hardware contention, warm caches and workload differences limit broad comparisons. VictoriaMetrics ran on its own service and storage layout.

On this dataset, manual ClickHouse SQL matches native ClickHouse results: maximum relative error among overlapping points `1.05e-14` (all 121 points shared). But VictoriaMetrics MetricsQL `rate` **does not have exact numerical parity** with ClickHouse PromQL `rate`: median relative difference about 3.18%, maximum 18.11%. We cannot call its faster rate result a semantically equivalent benchmark until this difference is resolved.

### Why the patch may help

`EXPLAIN PIPELINE` for the unpatched native expression showed **3 AggregatingTransform stages**; manual equivalent SQL showed **2 AggregatingTransform stages**. Both read through `timeSeriesSelector`, producing five read streams merged to one; the main materialized grid and duplicate-check stage are targets for the rewrite. The aim is to reduce work in the compiler SQL conversion, without changing the data model. The measured manual/native p50 ratio is 1.53x; this is a **potential** upper-level indication, not a measured patch speedup.

## Query log and evaluation-step sensitivity

`system.query_log` for the same 2h / 60s workload (unpatched ClickHouse) reports 371,792 rows and 404,334,285 logical bytes read for both native and manual SQL. Representative records:

| Path | Query duration | Peak query memory | Read buffer bytes | User CPU |
|---|---:|---:|---:|---:|
| Native | 3,010 ms | 276,704,480 B | 224,301,054 B | 2,175,115 us |
| Manual | 1,971 ms | 250,372,515 B | 206,054,139 B | 1,617,364 us |

The native plan read the same number of rows but used ~26.3 MB more tracked query memory and ~18.2 MB more buffer reads. Measured disk-read time was in milliseconds to tens of milliseconds, far below full query duration. The main cost is CPU and intermediate arrays/aggregations, not cold disk IO in this synthetic test.

Sensitivity to evaluation step for the same 2h range (unpatched; small sample counts, not statistically robust):

| Step | Points | Repeats | CH native p50 | CH manual p50 | VM p50 | Native/manual |
|---:|---:|---:|---:|---:|---:|---:|
| 15 s | 481 | 3 | 4,904 ms | 3,332 ms | 331 ms | 1.47 |
| 60 s | 121 | 5 | 3,010 ms | 1,969 ms | 284 ms | 1.53 |
| 120 s | 61 | 2 | 3,218 ms | 2,666 ms | 317 ms | 1.21 |

ClickHouse manual/native numerical agreement across those steps is better than `1.4e-14` maximum relative error. Results come from `bench_single_node.py`, with `--step 15|60|120`; they are benchmark evidence for evaluating the pending patch, not actual patched-binary results.

### Indexed reads

`EXPLAIN indexes=1 SELECT ... FROM timeSeriesSelector(...)` reported `42192-element set` matching the exact metric and **655/855** selected samples MergeTree granules across 5 parts (at `index_granularity=256`). The broad tags-to-ID lookup and the read of many series dominate work before a final 121-point output is produced. This is an indexed query, not a scan of every stored sample. Whether `timeSeriesIdToGroup` is itself a bottleneck remains unclear: two small tests grouped by raw ID and by group transformation had noisy, overlapping runtimes.

## Filter selectivity (unpatched baseline)

The exact metric `http_requests_by_route_total` has 94,464 label sets in the six-hour dataset. The tag filters below reduce this to 8,640 and 5,472 label sets respectively. For the same 2h range and 60-second evaluation step, three repeats per query gave:

| Exact selector | Whole-table tag count | CH native p50 | CH manual p50 | VictoriaMetrics p50 | Native/manual |
|---|---:|---:|---:|---:|---:|
| `http_requests_by_route_total` | 94,464 | 3,010 ms | 1,969 ms | 284 ms | 1.53 |
| `{project="search"}` | 8,640 | 937 ms | 716 ms | 65 ms | 1.31 |
| `{project="search",app="recommender-0"}` | 5,472 | 446 ms | 411 ms | 25 ms | 1.09 |

All three shapes retain full 121-point agreement between ClickHouse native and manual SQL (maximum relative errors `<1.1e-14`). This is evidence that the extra aggregation/check has a higher cost at larger cardinality; it does **not** establish patched-binary speedup. Exact selected time-range series counts may be lower than the table-wide tag counts shown here. VictoriaMetrics and ClickHouse differ in rate numerical semantics; their latency data are not exact correctness comparisons.

## CI and artifact handoff

- `ts-lab-build.yml` uses only the lab branch and the lab patch/workflow/script paths, not PRs or master; it checks out exact source SHA, verifies downloaded LLVM22 SHA256, applies patch, installs `ccache`, configures, runs `ninja -j2 clickhouse`, runs smoke and five regression tests, uploads the compressed binary plus SHA256 to a seven-day GitHub Actions artifact, and creates a prerelease only on success.
- Run `41283775632` failed: CMake could not find LLD. Fixed by selecting LLVM `LINKER_NAME` and adding LLVM to `PATH`.
- Run `41286573925` failed: no ccache/sccache. Fixed with apt install of ccache, cache action, and `-DCOMPILER_CACHE=ccache`.
- Run `41287227882` was still running when this report was written. Check: https://github.com/moleus/ClickHouse/actions/runs/41287227882
- An independent probe run **41287293230 succeeded**. It created a temporary prerelease, uploaded a small file, downloaded it through GitHub CLI, verified its SHA256, deleted the prerelease/tag, and uploaded an Actions artifact `13075990954`. The artifact ZIP also downloaded successfully through the GitHub connector into the test runtime, and `sha256sum -c` printed `payload.txt: OK`. The temporary probe workflow was removed afterward. **Upload/download is therefore verified**, including both release assets and Actions artifacts, for a small payload. Large ClickHouse binary download is not yet verified.
